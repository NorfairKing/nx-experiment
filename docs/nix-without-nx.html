Nix Without Nx

An experiment in packaging Vitest tests as granular Nix derivations, to stop rerunning every test when any file changes. It set out to import Nx's dependency analysis into Nix. It found there was nothing to import.

Verdict

For a pnpm workspace with isolated linking, Nix needs nothing from Nx.

Nx knows dependencies at exactly one level — project to project — and derives them from the package manifests. Nix can read those manifests during evaluation and produces a byte-identical set of derivations. One tsc derivation and one Vitest derivation per package is the granularity frontier. Everything below is the evidence, including the four conclusions that were wrong before they were right.

Every workspace edge is attributed to the project's manifest, so Nx is reading the same file Nix can read. Two probes confirm it from the other side: for an undeclared import of a workspace package, Nx reports no edge; for a cross-package tsconfig path alias, Nx reports no edge. Both fail the build loudly instead, because pnpm's isolated node_modules never linked the package.

03Evaluation does not grow with the workspace

Criterion 2 was the one that could still have sunk the approach: evaluation happens on every invocation, before any build. If it scaled linearly with project count, a 400-package workspace would pay about 1.6 s per nix build. It does not scale linearly. It barely scales at all.

Nor does package size matter

Evaluation copies every project directory into the store, so a workspace of large uneven packages could plausibly cost more than a uniform synthetic one. Measured at the same project count, one uniform and one with packages varying from 2 to 9 modules and files from 20 to 260 lines:

5.0 MBvaried source → 132 ms

04Where a derivation's time actually goes

One leaf package's test derivation, edited uniquely so it must rebuild, measured in parts rather than divided out of a total. This is the measurement that killed the plan to make derivations cheaper by sharing a workspace skeleton between them.

Amortise that fixed cost and the comparison inverts

Because evaluation is charged per invocation, building one unit looks expensive and building nineteen does not. Both figures are true; they answer different questions.

05What each kind of change invalidates

Thirteen classes of change, applied one at a time to a clean tree and reverted. For each, three counts out of 19: the projects nx show projects --affected reports, the Nx task hashes that changed, and the Nix derivation paths that changed.

Comparing Nix against Nx's affectedness would flatter Nix — affectedness is project-level and ignores target inputs. The task hash is the fair counterpart to a derivation path: both decide whether the work is reused.

Why the two disagreements happen

A test-only dependency. test-utils is a dev dependency of three packages. Nx's project graph reports dependencies and devDependencies both as type: "static", so ^sources propagates it transitively: 8 test tasks rehash. Nix invalidates 4, because test-utils never enters those packages' dist — the build derivation's closure literally does not contain it. Recovering the split costs one lookup per project in the manifests.

pnpm-workspace.yaml. It decides what counts as a workspace package and carries install-affecting settings. It is in no Nx named input, so a change to it rehashes nothing and would rerun nothing. Nix cannot miss it, because the install derivation reads it and every test depends on the install.

The shape is the same in both: in Nx an input exists because somebody declared it, and a missing declaration fails silently in the unsafe direction.

06Granularity: where to stop

Three granularities were built and measured: one derivation per package; one per test file with the whole project as input; one per test file with only that file as input.

source results/granularity.json
reproduce node scripts/granularity.mjs

For a source change the finer granularity is proportionally worse — 22/27 against 14/19 — because splitting a package into several nodes splits nodes that were going to be invalidated anyway. Only an edit confined to one test file benefits.

The cost side cannot be pinned down: two runs of the same measurement gave +18% and +2%, so "small" is all the data supports. The case against per-test-file granularity does not need it. It rests on the invalidation gain being negligible and on the hazard the split introduces — a test file missing from the enumeration gets no derivation, and every derivation that does exist still passes. Demonstrated by removing one: the workspace stayed green and four assertions never ran.

Where per-file granularity does pay is parallelism, and Nx shows it: splitting 19 units into 27 took Nx from 6 487 ms to 3 420 ms, because slow files stop queueing behind a package-level task. That is the one thing in this experiment worth taking from Nx — and Nx will compute the split for free while refusing to run the group target without Nx Cloud. The individual per-file targets run locally.

07Architecture D, measured and rejected

One candidate architecture was to generate Nix derivations from Nx's task graph rather than its project graph. Earlier drafts argued against it from the shape of the data and admitted it had never been built. Rather than build a parallel implementation, the claim is directly testable: compare the unit-and-edge set each graph would generate.

The five missing units are build-chain-a, build-cli, build-orphan, build-report, build-web — exactly the leaf projects nothing depends on, so ^build never pulls their build task in. Since Vitest does not typecheck, deriving from the task graph would leave a type error in any leaf package invisible to every check. The three spurious edges are the dev-dependency imprecision again, propagated into build ordering.

So the architecture that looked merely redundant is actively unsafe. That was the surprise of the exercise.

08Four conclusions that were wrong first

Included because the page's job is to let the work be checked, and because every one of these was caught by measurement disagreeing with itself rather than by review. If you want to find a fifth error, this is the shape it will have.

was"Nix does not buy speed — 7× slower on a one-file change."

isNix is faster on every aggregate case; ~1.4× slower on a single unit.

This machine runs a Nix post-build hook uploading every output to a binary cache. On one leaf unit that is 3 018 ms with the hook against 1 177 ms without — roughly two thirds of what had been reported as "the fixed cost per Nix derivation" was cache upload. It is charged per derivation, so it also interacts directly with the granularity choice. Every Nix figure on this page passes --option post-build-hook "".

was"Nx affected 0.68 s against Nix 45.9 s — 70× slower."

is6 377 ms against 3 758 ms. Nix is 1.7× faster.

The harness appended identical text every run, so it kept reproducing an edit whose derivations an earlier run had already built. Nx served a cache hit; the same bug ran in Nix's favour elsewhere, reporting 1.3 s for work that recompiles fourteen packages. Each harness mutation is now unique per run.

wasA cold-build column: 23.4 s per-package, 32.9 s per-test-file.

isWithdrawn. The same measurement gave 23 s and 80 s on consecutive runs.

It deleted only the test outputs and left every tsc output in the store, so "cold" meant "everything except the compilation" and drifted with whatever an earlier run had left behind. Defining it properly required deleting build outputs too — and nix store delete scans every GC root then walks /nix/store/.links, which on a store deduplicating 200 GiB, called once per path, took the machine down. The benchmark no longer touches the store; it forces work by changing an input instead.

was"Which package an import resolves to is the whole reason the bridge is worth anything."

isNx does not resolve it either. It reads the manifest.

A day went into designing a bridge to import Nx's dependency analysis. One jq query over Nx's file map would have shown the per-file deps field empty for all 88 TypeScript files. The lesson generalises: before building a bridge to another tool's analysis, check that the analysis exists. A field present in the schema is not a field with anything in it.

09Preconditions for your repository

The verdict is conditional. These are the conditions, and every command below has been run so that its real output is known — a check whose output you cannot interpret is worse than no check. The first two decide the architecture.

01An undeclared import must not resolve

# pick a package, and a workspace package it does NOT depend on
cd packages/<a-package>
node -e "require.resolve('@scope/<something-it-does-not-declare>')"

Want: failure, MODULE_NOT_FOUND, exit 1. Repeat for a package the manifest does declare — it must print a path, or the check is not discriminating. It needs pnpm install to have run: with no node_modules nothing resolves and the control cannot pass.

Do not use pnpm config get node-linker: it prints undefined in the normal passing case, so the answer looks like an error and says nothing about the tree that got installed.

If it fails: phantom imports resolve, the manifests under-report, and Nix would build a graph missing real edges. Use the generated-table override.

02No path mapping crosses a project boundary

grep -rn '"paths"' tsconfig*.json */*/tsconfig.json

Want: no output. grep exits 1, which means "found nothing", not "failed". If there is output, check whether any mapping's target lies outside the project declaring it; a mapping to ./src/* is harmless.

If it fails: the manifests are not the graph — and confirm Nx actually reports those edges before relying on it. Here it reported none.

03Tests import source, not the built output

for d in packages/*/ apps/*/; do
  name=$(jq -r .name "$d/package.json")
  grep -l "from '$name'" "$d"/tests/*.ts 2>/dev/null
done

Want: no output. Anything listed is a test importing its own package by name, which resolves through node_modules to the built output.

If it fails: add each package's own build to its test derivation's inputs. One extra edge per package, no loss of correctness.

04One real build target and one real test target per project

nx show project <a-project> --json | jq -c '[.targets | keys[]]'

Want: one thing to build and one way to test. Expect more entries than that — this workspace prints six, because the atomizer derives per-file targets and Nx adds its own nx-release-publish.

If it fails: several real targets per project is the one case where the task graph might express something the project graph cannot. Unexplored, not rejected.

05tsc is the builder, and no uncommitted generated sources

jq -r -s 'map(.scripts.build) | group_by(.) | map({script: .[0], count: length})' \
  packages/*/package.json apps/*/package.json

Want: a single group, and that group a plain compile. Here: [{ "script": "tsc -p tsconfig.json", "count": 19 }]. Several groups is fine as long as you read them; a && chain or a codegen prefix writing into src/ is the failing shape.

If sources are generated: commit them or generate them inside the derivation. Nix's filesets come from the git tree and so does Nx's file index, so neither sees an uncommitted generated file — it fails loudly rather than silently, but it does fail.

06Whether a post-build hook uploads to a cache

nix config show post-build-hook

Want: empty. Here it prints a store path to an upload script, which cost about 1 841 ms per derivation and swamped every figure in this experiment until it was disabled.

If it is set: count derivations before choosing a finer granularity. This is not a correctness precondition — it is the largest cost found, and it scales with exactly the granularity you are trying to buy.

10Three guards, because an inferred graph goes stale silently

A graph Nix inferred is an inference, and a wrong inference fails in one direction: fewer tests, still green. Closing that takes three checks, because the question has three parts. All three are in nix flake check.

QuestionCheckIndependent authority
Is every project present? nix build .#workspaceProjects pnpm, via pnpm list -r --depth -1 --json
Are the declared edges the ones the source imports? nix build .#build-<pkg>, all of them pnpm-strict resolution and tsc
Is every test file covered? nix build .#guard-<pkg> Vitest, via vitest list --filesOnly --json

Each was proven by breaking it deliberately. Dropping apps from the workspace globs silently takes the test derivations from 19 to 16; the guard exits 1 and names apps/cli, apps/report, apps/web. Removing a test file from the enumeration leaves the workspace green with four assertions unrun; the guard exits 1 and names the file.

The second row exists for a reason worth stating separately. A package's test derivation deliberately does not depend on its own build — the tests import src directly, which is a real precision win. But Vitest does not typecheck: Vite strips types without checking them. Combine the two and a type error in a leaf package with no dependants was invisible to every check in the flake. Confirmed by introducing one — test-orphan passed, build-orphan reported TS2322.

11What is still open

  • Content-addressed derivations. Blocked, not declined: this machine's Nix daemon does not have ca-derivations enabled, and it is refused at evaluation even with the flag accepted by the client and Trusted: 1. The prerequisite is done — .d.ts.map files are deleted from build outputs, because they were the only reason tsc output changed under a formatting-only edit, and nothing downstream reads them.
  • Deep import graphs and tsconfig project references at scale. The scaling workspace is layered but shallow, and package size has been tested but import depth has not.
  • Architecture D for multi-target projects. Measured and rejected for one build and one test target per project. Whether a task graph with several real targets expresses something the project graph cannot is untested.
  • The single-unit gap. 1 177 ms against Nx's 845 ms, of which 816 ms is evaluation. Amortised across an invocation Nix is ahead, so this only bites a loop that builds one package at a time. Whether Nix can be invoked once and told to watch is unexplored.
  • Your repository. Everything here is a 19-project hand-written workspace and a synthetic 400-project one. Section 09 is what to run on the real thing.
